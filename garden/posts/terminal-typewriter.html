Building the whoami terminal on my homepage

20 Nov 2025 · webdev, design, accessibility

This is a hand-built HTML post, and the terminal below is the real thing: it runs the exact same code that sits at the top of my homepage. Hover it, tap it, or focus it with the keyboard to reveal the full list; move away and the cycle resumes.

hris@hrc: ~ click to expand

hris@hrc:~$ whoami

hrishika roychoudhury. msis candidate, unc sils.

hris@hrc:~$ cat focus.txt

Areas of expertise: human-computer interaction, ai/ml evaluation, user experience, health informatics, neural networks, interdisciplinary research, data visualization, full-stack web development, accessible technology, osint, digital preservation, and archiving the now.

Why a terminal?

I wanted my homepage to say what I do without reading like a résumé bullet list. A little terminal that types out whoami and cat focus.txt felt more like me, with a nod to the command line and some personality.

The markup

The whole thing is one box. The first command line is static text. The second command, cat focus.txt, is followed by an empty paragraph whose data-terms attribute holds every focus area, separated by a | pipe. That empty paragraph is what the script types into. A hidden sr-only sentence repeats the full list in plain prose so screen readers get everything at once. 

<div class="terminal" id="terminal" tabindex="0">
  <div class="terminal-body">
    <p class="line"><span class="prompt">hris@hrc:~$</span> whoami</p>
    <p class="line out">hrishika roychoudhury. msis candidate, unc sils.</p>
    <p class="line"><span class="prompt">hris@hrc:~$</span> cat focus.txt</p>

    <!-- the empty line the script types into -->
    <p class="out expertise" id="expertise" aria-hidden="true"
       data-terms="human-computer interaction|ai/ml evaluation|user experience|..."></p>

    <!-- the same list, in plain prose, for screen readers -->
    <span class="sr-only">Areas of expertise: human-computer interaction, ...</span>
  </div>
</div>

The script

On load the script reads data-terms, splits it on the |, and animates one word at a time. The loop has two phases: typing adds a character and schedules the next tick a few milliseconds later (with a little random jitter so it feels human); once the word is complete it pauses, then deleting removes characters one by one until the line is empty, advances to the next term, and starts again, forever. Here is the core of it, lightly trimmed: 

const terms = target.dataset.terms.split("|").map(t => t.trim());

const TYPE = 55, DELETE = 28, HOLD = 1300, BETWEEN = 400; // milliseconds
let i = 0, pos = 0, phase = "typing";

function tick() {
  const term = terms[i];
  if (phase === "typing") {
    word.textContent = term.slice(0, ++pos);
    if (pos >= term.length) { phase = "deleting"; setTimeout(tick, HOLD); }
    else setTimeout(tick, TYPE + Math.random() * 45);   // jitter
  } else {
    word.textContent = term.slice(0, --pos);
    if (pos === 0) { i = (i + 1) % terms.length; phase = "typing"; setTimeout(tick, BETWEEN); }
    else setTimeout(tick, DELETE);
  }
}

// Respect the OS "reduce motion" setting: skip the animation entirely
// and just render the full list at once.
if (matchMedia("(prefers-reduced-motion: reduce)").matches) showAll();
else tick();

Keeping it accessible

The catch with typewriter effects is that they can be hostile to screen readers and to people who get motion-sick. So the animated line carries aria-hidden="true" (assistive tech ignores it), the full list of focus areas lives in that screen-reader-only sentence, and anyone with reduce motion turned on skips the animation and just sees the complete list. Clicking or focusing the terminal also pins the full list open, so nobody is forced to wait for the cycle.
