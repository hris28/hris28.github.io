What your browser silently sees

20 Jun 2026 · privacy, security, web

A rabbit hole I keep falling back into: how much can a website learn about me, without any login or interaction, just from opening the page. The answer is "a startling amount," and the unsettling part is that these signals combine into a near-unique fingerprint that follows you even with cookies cleared.[1] So I built something to read it all back to you, running entirely in your browser.

What this is actually showing

None of this required permission. The browser hands it over to make pages work: your screen size so layouts fit, your language so text localizes, your GPU so graphics render. Individually it's harmless. Combined, the set of values is distinctive enough that researchers found most browsers are uniquely identifiable from these traits alone, a technique called browser fingerprinting.[2] Unlike a cookie, you can't delete a fingerprint.

Reading the blanks: where each value lives and who can see it

A line that says "not available" or "not exposed" does not mean the fact about you does not exist, or that no one can know it. It just means your browser's JavaScript did not hand that value to this page. Whether you are still exposed depends on which of three places the data actually lives.

  • Read locally by JavaScript (everything in the panel above). If it is blank here, this page could not read it. That is a real, verifiable win when the browser withheld it on purpose.
  • Seen by the network no matter what JavaScript does. Your public IP is the headline example: local scripts cannot read it, which is why the lookup at the bottom needs an outside service, yet every server you connect to sees it automatically because it is part of the connection itself. The WebRTC row makes the same point, surfacing local and sometimes real IP addresses that ordinary scripts are not meant to expose.[1]
  • Inferred indirectly. Even when one signal is blocked, a tracker can often estimate the same thing another way: screen size hints at device class, request timing hints at connection speed. Blocking a vector raises the cost; it rarely deletes the fact.

So a blank in the panel means "this channel was closed," which is genuinely informative, but it is not a clean bill of privacy, because the network layer and cross-method inference live outside what any in-page script can read.

Why the same value shows in one browser and not another

None of these values is pulled from a hidden file. Each one exists only because a browser chose to implement a JavaScript interface that returns it, and browsers disagree about which interfaces to ship. That disagreement is exactly why "GPU renderer" or "device memory" appears in Chrome but is blank in Firefox or Tor. Three different mechanisms sit behind a blank:

  • The browser never implemented the API. navigator.deviceMemory (the Device Memory API) and the connection group (navigator.connection, the Network Information API) are Chromium-only. Chrome, Edge, and Brave ship them; Firefox and Safari deliberately never did, in part because they add fingerprinting surface for little user benefit. Your RAM and your connection speed are perfectly real. The browser just offers no property for a script to read them, so the value is undefined and the tool prints "not exposed."[3]
  • The browser implemented it, then deliberately neutralized it. Your GPU vendor and renderer come from a WebGL extension called WEBGL_debug_renderer_info. Standard Chrome returns the real string (for example "ANGLE (NVIDIA GeForce RTX...)") because games and graphics apps legitimately want it. Brave and the Tor Browser intercept that exact call and return a generic or empty value on purpose, because the precise GPU and driver is one of the most identifying things a page can learn. The difference you see is not your hardware changing; it is the browser deciding whether to answer. The Battery Status API is the end state of this approach: Firefox and Safari did not just blank it, they removed it entirely after it was shown to aid tracking.
  • It needs a secure context or a user action, or it simply does not apply. Some APIs only work over HTTPS or after you interact with the page. And some blanks are honest absences: maxTouchPoints is 0 on a non-touch laptop, there is no battery to report on a desktop, and screen orientation is often unset outside mobile.

Two more reasons are not about the browser at all. A value you control and have not set shows "not set" (Do Not Track and Global Privacy Control are blank because you are sending no such signal), and a request that something blocked simply fails (if the IP lookup errors, a tracker blocker stopped that one call, although your IP is still exposed to every server you actually connect to).

How to tell which case you are in

Three checks turn a blank from a mystery into a known quantity:

  • The console. Open developer tools and type the exact property, for example navigator.deviceMemory or navigator.getBattery. If it returns undefined, this browser does not expose it, which is proof it is a browser gap rather than missing hardware.
  • The compatibility tables. MDN documents, per browser and version, which interfaces are implemented. That is how we know deviceMemory and the Network Information API are Chromium-only and that Firefox and Safari dropped the Battery API, rather than guessing.[3]
  • Compare browsers, and use the external lookup. Open this page in Chrome and the blank "device memory" fills in, which proves the value exists and only the browser was withholding it. The IP lookup returning your address proves the network sees what local scripts could not.

What data makes up a fingerprint

For these same mechanisms framed as separate ideas (cookies vs pixels vs fingerprinting), see Cookies, pixels, and fingerprinting.

  • User-Agent string: Your browser sends this with every request. It contains the browser name and version, the operating system, and sometimes device information. Example: Mozilla/5.0 (Windows NT 10.0; Win64; x64) AppleWebKit/537.36.
  • Screen resolution and color depth: Available to any JavaScript running on the page.
  • Installed fonts: Websites can probe which fonts are installed by rendering text and measuring its dimensions. Different operating systems and users have different font sets.
  • Canvas fingerprint: A website can instruct your browser to draw a hidden image using the HTML Canvas API. The rendered result varies subtly across different GPUs, drivers, and operating systems, consistently for a given device, so the hash of the image becomes a stable identifier.[2]
  • WebGL fingerprint: Similar to canvas fingerprinting, using the WebGL API to identify GPU and driver combinations.
  • Audio context fingerprint: The Web Audio API processes audio signals slightly differently across hardware. A fingerprint can be derived from those differences without playing any audible sound.
  • Timezone and language: Your timezone and preferred language are disclosed in headers and available to JavaScript.
  • Browser plugins and extensions: The presence of extensions changes how your browser behaves, and some are detectable.
  • Do Not Track header: Ironically, setting the Do Not Track header makes your browser slightly more distinctive, because fewer browsers send it.
  • Battery status: Historically available through the Battery Status API. Most browsers have removed or restricted it due to fingerprinting risk, but it shows how any API exposing hardware information is a potential fingerprinting vector.

None of these is particularly unique on its own. Combined, they often single out one browser among millions. Each value you reveal carries some "bits of entropy," information theory's measure of how much it narrows the crowd, and they add up.[10] Peter Eckersley's 2010 Panopticlick study put numbers on it: of 470,161 browsers tested, 83.6% had a unique fingerprint from a handful of characteristics, rising to 94.2% among those running Flash or Java.[4]

How this tool builds your fingerprint

Here is the whole recipe, start to finish. First the tool gathers a set of signals: properties your browser hands any script that asks. These include your user-agent and platform, your languages, your CPU core count, your screen and window sizes, color depth and pixel ratio, your GPU's vendor and renderer strings (read through WebGL), and your time zone.

Then it adds the highest-value signal: a canvas signature. A canvas is an off-screen drawing surface. The tool paints the text "garden fingerprint" twice, in a fixed font, colour, and position, then calls toDataURL(), which exports the finished pixels as one long text string. The exact pixels depend on how your GPU, graphics driver, and OS rasterise fonts and blend the half-transparent layer, so the same machine returns a byte-identical string while a different device returns a different one. That is why canvas is so identifying.[2]

Next it joins everything into a single long string, separated by |: the canvas data, then the Browser & OS block, the Screen & display block, the GPU strings, and the time zone. Finally it runs that string through a hash function called FNV-1a. A hash function is a fixed recipe that turns an input of any length into a fixed-size number: the same input always gives the same number, and you cannot run it backwards. FNV-1a starts from a fixed seed, then for each character it folds that character in with an XOR and multiplies by a large prime, discarding everything above 32 bits (which simply wraps the number around). The eight hex digits after the # are that final number written in base 16.

Two things follow. The hash is deterministic: identical signals always produce the identical id. And it has an avalanche effect: change a single character anywhere in that long string and the multiply-and-mix cascade throws the final number somewhere unrelated, so the id changes completely rather than a little.

That avalanche is exactly why your screen affects the id. The Screen & display block is part of what gets hashed, so on the same browser and device a laptop panel and a plugged-in external monitor report different screen.width and screen.height (and usually a different devicePixelRatio: 2 on a Retina laptop versus 1 on a standard monitor). That changes several characters of the input, and therefore the entire id. Even just resizing the window changes the viewport numbers and shifts the id. This brittleness is the tool's main weakness, and it is deliberate and visible.

Notice what is not in the recipe: your IP address and location. The tool fetches those separately and only displays them; they never enter the hash, so the #id stays the same no matter what your IP is. That mirrors how fingerprinting is defined in the first place, as tracking "by the configuration and settings information [browsers] make visible to websites, rather than traditional tracking methods such as IP addresses and unique cookies."[11] So a VPN, which only changes the IP row, leaves your id untouched.

My version is deliberately simple, and weaker than a real tracker in two ways. First, it uses a handful of signals, whereas production libraries like the open-source FingerprintJS combine more than forty, including canvas, WebGL, audio, and font probes.[6] Second, my single hash is brittle. Real fingerprinters avoid that by storing each signal separately and using fuzzy matching: rather than demanding an exact match, they measure how similar a returning profile is to a stored one and re-link you once enough of it agrees. The research system FP-STALKER showed this can be done with a mix of hand-written rules and machine learning that decides how many attributes may differ, and by how much, so an updated driver or a new monitor does not break the link.[8] You can watch fuzzy matching happen in CreepJS, which computes a deliberately fuzzy hash that survives small changes, and in the FingerprintJS demo, whose visitor id persists across incognito windows.[9] The idea is identical to mine; theirs is just bigger and more forgiving.

How real websites go further

This demo stops at what your browser volunteers. Commercial trackers add layers on top:

  • IP geolocation - your address maps to a city/region and your internet provider.
  • Cross-site tracking - the same third-party scripts on many sites stitch your visits together.[1]
  • Tracking pixels - invisible 1×1 images that report when you opened an email or page.
  • Third-party cookies - persistent IDs shared across sites. Safari and Firefox block them by default; Chrome planned to phase them out but reversed course in 2024 to 2025, so they remain on by default there.[5]

What you can actually do

  • Use a tracker-blocking browser or extension (uBlock Origin; Firefox or Brave with strong defaults).
  • Turn on Global Privacy Control / "Do Not Track" where available.
  • Block third-party cookies in your browser settings.
  • A VPN hides your IP and approximate location (it doesn't stop fingerprinting, since the IP is not part of the fingerprint).
  • For the strongest fingerprint protection, use the Tor Browser, which makes everyone's fingerprint look identical, or Brave, which randomises it. Resist hand-editing a single value: changing just one attribute usually makes you rarer, not safer.[2]
  • Test yourself against a real tracker with EFF's Cover Your Tracks.[1]

See it from the other side

If you want the raw view, not just a summary of what each actor sees:

  • What a server receives from you: httpbin.org/headers and /ip echo back the exact HTTP headers and IP address your browser hands every site.
  • A fuller fingerprint than this demo: BrowserLeaks and AmIUnique show far more signals and how rare your configuration is.
  • What your ISP collects: the FTC's 2021 staff report examined six major US providers and what they gather and share.[7] More on this in what your ISP can see.
  • What a VPN changes: it moves that visibility to the provider, so whether they keep logs is the whole question. See VPN.
